# SRBench seed provenance and benchmark randomness bias

**Status (2026-10-29).** We suspected that the SR literature's shared benchmark seeds (15-bit values, fed to MT19937) inflate reported results. A 10-seed experiment under MCTS-4-SR's old C++ defaults suggested a ~1.6× effect. It did not hold up at scale: 100-seed runs on Nguyen (12 problems) and Livermore (22 problems) with the repo's current hyperparameters show recovery rates within 0.3% across MT19937 + SRBench seeds, MT19937 + quantum-random seeds, and PCG64DXSM + quantum-random seeds. Whether a seed effect exists under the paper's own hyperparameters (Table 4: c=1, gp_rate=0.2, ε=0.2) at 100 seeds is untested.

## Seed origin

The 100 benchmark seeds used across the SR literature originate from **SRBench** (La Cava et al., commit `a0b3e89`, 2020-12-16):

```python
# generated by calling
# In [1]: import numpy as np
# In [2]: np.random.seed(42)
# In [3]: np.random.randint(2**15-1, size=100)
```

All 100 values are in `[0, 32767)` (15-bit). Repository: [cavalab/srbench](https://github.com/cavalab/srbench), file `experiment/seeds.py`.

**Every SR method benchmarked in the recent literature uses this same list.** DSR, NGGP, PySR, gplearn, TPSR, DGSR, and MCTS-4-SR all inherit these 100 seeds from SRBench (directly or transitively via prior papers that used SRBench). None of the checked repositories (DSR, DGSR, TPSR) generate their own benchmark seed list — they either use SRBench's protocol or sequential seeds starting from a fixed value.

## MCTS-4-SR's copy

MCTS-4-SR copied the list into `imcts/benchmarks/executor.py` (or `iMCTS/benchmarks/runner.py` pre-rename) with one modification: **positions 4–9 and 10–15 are swapped** relative to the SRBench original. The rest (positions 0–3 and 16–99) are identical. Verified by mapping all 100 values back to `RandomState(42).randint(0, 32768, size=100)` — the list is a permutation of the first 100 outputs.

## RNG usage across the ecosystem

SRBench's runner calls `np.random.seed(random_state)` (MT19937) and passes the same seed to each estimator. Every method in the comparison table uses MT19937:

| Method | RNG |
|---|---|
| SRBench framework | `np.random.seed()` → MT19937 |
| MCTS-4-SR | C++ `std::mt19937_64` |
| DSR | `np.random.seed()` → MT19937 |
| PySR | Julia `MersenneTwister` |
| gplearn | `np.random.RandomState()` → MT19937 |
| TPSR | `np.random.seed()` → MT19937 |

## The hypothesis and the 10-seed experiment

MT19937's state is 624×32 = 19968 bits, initialized from a single seed via a linear recurrence. Small seeds produce poorly diffused initial states with correlated early outputs. If authors tune hyperparameters against the same 100 small seeds, the published settings could be implicitly calibrated to those MT19937 streams — train/test leakage that stays invisible because every method uses the same "test set".

The experiment that raised the suspicion (Nguyen-3, 10 seeds per cell, median evaluations to solution, old C++ defaults c=4, gp_rate=0.2, ε=0.2):

| Config | SRBench seeds | Random 32-bit seeds |
|---|---|---|
| MT19937, upstream (`0d2a771`) | 164k | 258k |
| PCG only (N=0), our code (`bdc28a1`) | 228k | 187k |
| PCG + matched-pair (N=4) | 97k | 432k |

On these numbers MT19937 looked ~1.6× faster on SRBench seeds than on random ones, PCG showed no such gap, and matched-pair's 2.35× speedup on SRBench seeds turned into a 2.3× slowdown on random seeds. With 10 seeds per cell this is weak evidence: per-seed evaluation counts on Nguyen-3 span more than an order of magnitude (e.g. 36k to 469k in `huang2025_hotpaths_regression.md`), so cell medians move by this much from sampling alone. The matched-pair reversal stands as a result about matched-pair — its gain did not survive fresh seeds — but the experiment did not establish a seed bias. The 100-seed runs below were the test.

## Comparison methodology in the paper

Huang et al. (2025) use all 100 seeds, one run per seed, 2M eval budget. Comparison numbers for DSR, NGGP, PySR, etc. are **cited from prior publications**, not re-run. All prior publications also used SRBench seeds. No independent evaluation exists.

## Quantum random seeds for unbiased benchmarking

For controlled experiments we use seeds from the ANU Quantum Random Number Generator
(quantum vacuum fluctuations, homodyne detection; Symul et al., *Applied Physics Letters* 2011).

- Service: https://quantumnumbers.anu.edu.au
- API key: see Claude memory (not committed to repo)

This eliminates any PRNG-related objection to the replacement seed set: the seeds
are physically random, not generated by any deterministic algorithm.

## Livermore with R (constant token) — partial, 2026-05-13

The paper omits R for Nguyen/Livermore (Table 4: "Omit constant"). This makes
several problems artificially unsolvable (e.g. `4x⁴+3x³+2x²+x` without constants).
We re-ran PCG+quantum with R added. Partial results (29–40 seeds per problem, run stopped early).

| Problem | Formula | Without R | With R | Notes |
|---|---|---|---|---|
| Livermore-6 | `4x⁴+3x³+2x²+x` | 26% | **100%** | Needs constants 4,3,2 |
| Livermore-7 | `sinh(x)` | 7% | **100%** | Needs 0.5 for `(eˣ-e⁻ˣ)/2` |
| Livermore-8 | `cosh(x)` | 27% | **100%** | Same |
| Livermore-10 | `6sin(x)cos(y)` | 59% | **100%** | Needs constant 6 |
| Livermore-17 | `4sin(x)cos(y)` | 74% | **100%** | Needs constant 4 |
| Livermore-18 | `sin(x²)cos(x)-5` | 28% | **100%** | Needs constant 5 |
| Livermore-3 | `sin(x³)cos(x²)-1` | 100% | **43%** | Regression — R expands search space |
| Livermore-14 | `x³+x²+x+sin(x)+sin(x²)` | 95% | **49%** | Same — harder with constants |
| Livermore-9 | degree-9 poly | 4% | **0%** | Depth-limited (impossible at depth 6) |
| Livermore-21 | degree-8 poly | 47% | **7%** | Depth-limited |
| **Overall** | | **72.5%** | **88.8%** | +16% despite regressions |

All 12 problems not listed reach 100% with R (Livermore-5 and -22 on 39 seeds, the rest on 40).

**Key finding:** Adding R fixes all constant-limited problems (100%) but makes some
problems worse — the larger search space (R adds a branching action at every node)
hurts problems that don't need constants. Livermore-3 drops from 100% to 43%.

**No problem within structural reach is hard for the search.** Every Livermore problem
except the two depth-limited ones (9, 21) is solved at ≥94% under one of the two settings:
with R for the constant-limited problems, without R for Livermore-3 and -14. Those two drop
only because R enlarges the search space; without R upstream recovers them at 99–100% and
94–99% with the correct structure. An earlier version of this note called them the only
genuinely hard problems and picked them for matched-pair testing — that was wrong.

Raw data: `../mcts4sr/results/livermore_with_R/` (partial).

## Matched-pair on Livermore-3 and -14 (2026-05-13)

PCG + quantum seeds, with R, **old HP** (c=4, gp_rate=0.2, ε=0.2, max_constants=6) —
the exploration-heavy regime where MP previously showed 2.4× speedup on Nguyen-3.

| Problem | Target | MP N=4 recovery | MP N=4 med evals |
|---|---|---|---|
| Livermore-3 | `sin(x³)·cos(x²) - 1` | **82%** | 551,805 |
| Livermore-14 | `x³+x²+x+sin(x)+sin(x²)` | **35%** | 2,000,001 |

Compare with upstream YAML HP (c=6, gp_rate=0.5, ε=0.1, no MP, partial ~40 seeds):
Livermore-3 43%, Livermore-14 49%. Not directly comparable (different HP). Without R,
upstream solves both at ≥94%, so MP has nothing to rescue here.

### Failure analysis

All failures are **numerically near-perfect** (reward >0.9997, test R² ~1.0) but
miss the 1e-6 threshold with a different structure. The method finds alternative
formulas that nearly match on [-1,1]:

**Livermore-3 failures** (18/100): mostly `sin(C·x²)` with polynomial envelope
instead of `sin(x³)·cos(x²)`. Arguably simpler — one trig call vs two.

**Livermore-14 failures** (65/100): two patterns:
- Near-misses: `0.833·x³ + x·(x+2.02) + sin(x·(x-0.019))` — finds sin(x²) but
  absorbs sin(x) into polynomial coefficients (on [-1,1], sin(x)≈x so the method
  merges them). `sin(x·(x-0.019))` is simpler than `sin(x)+sin(x²)`.
- Completely different: products of cos/sin/exp terms that happen to match on [-1,1].

**Observation:** The benchmark's recovery metric penalizes the method for finding
**simpler, nearly equivalent** formulas. On [-1,1] with 20 samples, many structurally
different expressions are numerically almost indistinguishable from the target. This is a
limitation of the benchmark, not the method.

### N sensitivity

| | MP N=4 | MP N=6 |
|---|---|---|
| Livermore-3 | **82%**, 552k evals, 51s | 77%, 751k evals, 69s |
| Livermore-14 | 35%, 2M (budget) | 38%, 2M (budget) |

N=6 is worse than N=4 on Livermore-3 (more overhead per transition, no better

## Summary of findings

1. **No measurable seed effect** with the repo's current hyperparameters (c=6, gp_rate=0.5, ε=0.1).
   Both Nguyen (93.6–94.2%) and Livermore (72.3–72.6%) vary by <0.3% across
   MT19937+SRBench, MT19937+quantum, and PCG+quantum.

2. **Upstream changed the hyperparameters after publication** without explanation (commits 04e143a, 6012a9d).
   Paper Table 4 says c=1, gp_rate=0.2, ε=0.2; repo YAML uses c=6, gp_rate=0.5, ε=0.1.
   The change moves the search toward more GP mutation and less random exploration.

3. **The earlier 10-seed experiments** (Experiments 1–5 in `huang2025_hotpaths_regression.md`)
   used the old C++ defaults (c=4, gp_rate=0.2, ε=0.2), where structural failures were common
   (5/10 on Nguyen-3). Their apparent seed effect is within 10-seed sampling noise and was
   not confirmed. Open question: a 100-seed run under the paper's Table 4 settings.

4. **Adding R to Livermore** raises overall recovery from 72.5% to 88.8% but introduces
   regressions on problems that don't need constants. The paper's decision to omit R
   for Livermore is questionable.

5. **Ground-truth benchmarks are saturated for this method.** With the right operator set per
   problem, everything within depth 6 is solved at ≥94%. Remaining failures are depth-limited
   or near-equivalent alternatives on a narrow domain, not search failures — so matched-pair
   and seed quality have nothing left to improve here.
